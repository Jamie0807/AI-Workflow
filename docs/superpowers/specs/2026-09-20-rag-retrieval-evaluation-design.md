# 自动化 RAG 检索质量评测设计

## 目标

为 AI Workflow 增加可重复运行的 RAG 检索质量评测能力，使用人工标注的真实查询与相关 chunk 作为标准答案，比较向量、全文和混合检索，并能识别相对固定基线的质量回归。首版提供评测工具和数据格式；在真实数据完成标注前，不发布或伪造项目质量基线。

## 现状与约束

- `packages/ai-engine` 已提供 `RetrieverService` 和 `HybridRetriever`，支持 `vector`、`fulltext`、`hybrid` 三种模式。
- 知识库检索 API 使用 Ollama Embedding 和 Qdrant；全文检索目前由 Qdrant `textSearch` 提供。
- Knowledge Base 的 Embedding 模型、维度、topK、阈值和向量权重保存在 PostgreSQL。评测必须读取对应 Knowledge Base 的配置，不能悄悄使用与线上不同的默认值。
- 文档处理生成的 chunk ID 为 `${documentId}_${chunkIndex}`。重新切分文档可能改变 chunk 内容或索引，届时需要复核并更新标注。
- 现有手工检索界面和 Retriever 单元测试不构成相关性标注评测集。

## 方案与取舍

采用“共享检索组件 + 纯评测核心 + 工作流应用 CLI”的组合方案：

1. 将当前 API 中构造 Qdrant 全文检索 provider 的逻辑抽到可复用的 AI Engine 工厂，API 与评测 CLI 共用它，避免评测与产品检索行为漂移。
2. 在 AI Engine 的 knowledge evaluation 模块实现数据校验、排序指标和评测聚合。该层只接收评测样例与 `RetrieverService`，不依赖 PostgreSQL、Qdrant、Ollama 或文件系统，便于快速、确定性地单测。
3. 在 `apps/workflow` 增加 CLI：读取 JSONL 评测集，通过 Prisma 获取每个 Knowledge Base 的检索配置，使用与应用相同的 Ollama、Qdrant、检索器执行查询，并写出 JSON 和 Markdown 报告。

不采用仅用合成语料做质量基线的方案，因为它无法代表项目真实检索效果。合成样例只用于自动化测试。也不把评测仅做成 UI 功能：CLI 更适合复现、版本管理和后续 CI 集成。

## 评测数据格式

评测集使用 UTF-8 JSONL，每行一个样例，建议纳入版本控制。首版字段：

```json
{
    "id": "faq-login-001",
    "query": "如何重置登录密码？",
    "knowledgeBaseId": "<真实知识库 ID>",
    "relevantChunks": [
        { "chunkId": "<真实 chunk ID>", "relevance": 3 },
        { "chunkId": "<另一个相关 chunk ID>", "relevance": 1 }
    ]
}
```

- `id`：数据集内唯一的样例标识。
- `query`：非空用户查询。
- `knowledgeBaseId`：要评测的真实知识库 ID。
- `relevantChunks`：至少一个相关 chunk；`relevance` 是大于等于 1 的整数等级，首版限制为 1–3。未列出的 chunk 视为不相关。
- 数据校验拒绝空数据集、无相关项、重复样例 ID、非法等级和不完整字段；错误报告指出文件行号及样例 ID。
- 评测报告包含数据集 SHA-256。数据集变更时不能直接与旧数据集的报告作回归比较。

真实数据由项目成员按查询逐条检查并人工标注。标注指南要求覆盖常见意图、同义表达、关键词查询及近似主题/低相关查询；只有确认相关的 chunk 才标为相关。首版指标要求每条查询至少有一个相关 chunk，因此不纳入“整个知识库均无答案”的拒答评测。chunk 切分或文档更新后复核受影响标注。

## 指标定义

对每个查询计算指标，再对查询做宏平均；报告保留样例数与各查询结果，不能静默排除失败或无相关项样例。

- `Precision@K`：前 K 个位置中的相关 chunk 数除以 K；结果不足 K 时，缺失位置计为不相关。
- `Recall@K`：前 K 个结果中相关 chunk 数除以标注的相关 chunk 总数。
- `MRR@K`：首个相关结果排名倒数；前 K 无相关结果时为 0。
- `nDCG@K`：使用分级相关性，gain 为 `2^relevance - 1`，discount 为 `log2(rank + 1)`，以理想排序归一化；IDCG 为 0 的样例由数据校验拒绝。
- `p50`、`p95` 检索延迟：以每条检索调用的单调时钟计时，作为运行诊断信息，不混进质量分数。

每个检索模式单独报告指标。不同模式的相似度分数标度可能不同，不比较原始 score。

## 运行与报告

- CLI 参数支持评测集路径、模式（可一次选择一种或多种）、K、阈值、混合向量权重、输出目录和可选基线文件。
- Knowledge Base 的 Embedding 模型、维度、默认检索配置从数据库读取；显式命令行参数覆盖对应的检索参数。报告记录有效参数、Knowledge Base ID、Embedding 模型/维度、Qdrant collection、模式、时间、数据集哈希和 Git revision。
- CLI 对查询执行只读检索，不写向量或修改知识库数据。数据库、Qdrant 或 Ollama 不可用、Knowledge Base 不存在、评测数据非法、任一查询执行失败时，命令以非零状态退出并说明原因；不跳过失败项或伪装成通过。
- 输出一份机器可读 JSON 结果和一份便于审阅的 Markdown 汇总，包含模式、配置、指标、延迟、样例结果和失败详情。
- 基线比较要求数据集哈希、K 和被比较模式一致。质量指标低于基线的容忍范围时返回非零状态；延迟先报告但不作默认回归门禁，以免外部服务抖动造成不稳定失败。未提供已审阅基线时只生成报告，不声称质量通过。
- CI 默认执行纯指标、数据校验和评测聚合的单元测试。真实服务评测作为显式集成命令运行；集成依赖缺失必须失败，不得被测试框架静默 skip。

## 测试策略

- 指标单测覆盖完全命中、排序颠倒、结果不足 K、无命中、分级相关性和宏平均。
- 数据解析单测覆盖有效 JSONL、非法 JSON、重复 ID、空查询、无相关项和非法 relevance 等级，并验证错误定位。
- 评测器单测注入确定性 `RetrieverService`，验证各查询调用参数、延迟记录、逐条结果和宏平均；任何查询失败都导致运行失败。
- CLI/集成验证使用真实 PostgreSQL、Qdrant 和 Ollama 配置，确认三个模式都能执行、生成两种报告、比较基线和在依赖缺失时失败。CI 单测不要求连接真实服务。

## 非目标

- 不评估 LLM 生成答案的忠实度、完整度或主观质量。
- 不自动生成或自动裁决真实数据的相关性标签。
- 不在首版引入 reranker、调参搜索、在线监控或新的 Web 评测 UI。
- 不提交基于虚构数据或未经人工确认的质量基线。

## 完成标准

1. 有版本化 JSONL 格式及人工标注说明，非法评测集会给出明确错误。
2. 三种检索模式可在真实知识库上被同一 CLI 重复评测。
3. 报告含 Precision@K、Recall@K、MRR@K、nDCG@K、p50/p95、运行配置和数据集哈希。
4. 同数据集与配置下可比较固定基线，质量回归以非零状态报告；缺少外部服务时评测失败而非跳过。
5. 指标、数据校验和聚合逻辑有确定性自动化测试；没有将合成样例误认为真实质量基线。
