# AI Workflow 项目规划与核心机制

本文档用于沉淀 AI Workflow 作为个人项目上线时的实施计划、后续开发方向，以及当前项目中 RAG 和上下文管理的核心流程。

## 1. 作为个人项目上线计划

### 1.1 上线目标

第一阶段建议按“个人可用、稳定演示、方便维护”的目标上线，而不是一开始就做复杂的企业级部署。

上线后的最小可用形态：

- 可以通过域名访问主工作台。
- 可以注册、登录、创建工作流、运行工作流。
- 可以上传知识库文档，并完成向量化、检索和 RAG 节点调用。
- 可以通过发布后的 Web App 或 API 调用工作流。
- 服务重启后数据不丢失，有基础备份方案。

### 1.2 推荐部署形态

个人项目建议先使用单台云服务器加 Docker Compose 部署，后续有真实用户或流量后再拆分。

建议组件：

| 组件        | 用途                      | 初期部署建议                 |
| ----------- | ------------------------- | ---------------------------- |
| Next.js     | 主工作台与前端页面        | 和服务端一起部署             |
| API Server  | 外部 API 调用入口         | 同机部署，单独端口或子域名   |
| PostgreSQL  | 业务数据、账号、工作流    | Docker 容器挂载持久化目录    |
| Qdrant      | 向量数据、知识库切片检索  | Docker 容器挂载持久化目录    |
| Ollama      | 本地 LLM 与 Embedding     | 可同机部署，但要关注资源压力 |
| Nginx/Caddy | 反向代理、HTTPS、域名转发 | 推荐 Caddy 或 Nginx          |

域名规划可以先保持简单：

- `workflow.example.com`：主工作台。
- `app.example.com`：已发布工作流访问端。
- `api.example.com`：外部 API 调用入口。

如果只是个人使用，也可以先只部署一个主域名，把 API 和 Web App 通过路径或端口区分。

### 1.3 上线前准备

代码和配置：

- 确认 `.env` 或生产环境变量完整，不把密钥提交到仓库。
- 确认 `DATABASE_URL` 指向生产 PostgreSQL。
- 确认 `QDRANT_URL` 指向生产 Qdrant。
- 确认 `OLLAMA_BASE_URL` 指向可访问的模型服务。
- 设置强随机的 `JWT_SECRET`。
- 配置 SMTP，用于注册、验证或通知类邮件。
- 确认生产构建命令 `pnpm build` 可以通过。
- 确认 Prisma migration 能在生产环境执行。

数据准备：

- PostgreSQL 数据目录必须持久化。
- Qdrant 数据目录必须持久化。
- 准备数据库备份脚本。
- 准备 Qdrant snapshot 或数据目录备份方案。
- 如需初始化管理员账号，使用脚本或受控接口完成，不建议手动改库作为长期方案。

服务器准备：

- 安装 Docker、Docker Compose、Node.js、pnpm。
- 开放必要端口，关闭无关端口。
- 配置 HTTPS 证书自动续期。
- 配置防火墙和 SSH 登录安全策略。
- 准备日志查看和重启命令。

### 1.4 上线步骤

推荐按下面顺序执行：

1. 在服务器拉取仓库代码。
2. 配置生产环境变量。
3. 启动 PostgreSQL、Qdrant、Ollama 等基础服务。
4. 执行 Prisma migration。
5. 执行依赖安装和项目构建。
6. 启动主应用、Web App、API Server。
7. 配置反向代理和 HTTPS。
8. 使用浏览器完成登录、创建工作流、运行工作流的冒烟测试。
9. 上传一个小文档，验证知识库切片、向量化和检索结果。
10. 调用一个已发布工作流，验证外部访问链路。

### 1.5 验收清单

上线完成后至少确认：

- 首页、登录页、工作台页面都可以通过域名访问。
- 用户注册、登录、退出正常。
- 工作流创建、保存、编辑、运行正常。
- LLM 节点可以调用模型并返回结果。
- 知识库文档可以上传、处理、检索。
- RAG 节点可以在工作流中使用知识库结果。
- API Key 可以创建，并能调用发布后的工作流。
- PostgreSQL 和 Qdrant 重启后数据仍然存在。
- 服务器重启后服务可以恢复。
- 生产环境没有暴露本地开发密钥。

### 1.6 初期风险

- Ollama 本地模型对 CPU、内存和磁盘要求较高，低配服务器可能响应慢。
- Qdrant 保存的是向量数据，不能只备份 PostgreSQL。
- 如果 API 公开，需要增加频率限制和调用日志。
- 如果没有 CI/CD，手动部署时要严格记录命令和版本。
- 邮件服务不稳定会影响注册和通知流程。
- 个人项目也要尽早处理密钥泄露、弱密码和公网数据库暴露问题。

## 2. 后续开发计划

### 2.1 产品能力

优先级较高的产品方向：

- 增加工作流模板，让用户可以直接从常见场景开始。
- 增加节点搜索、节点分组、节点复制和快捷编辑能力。
- 增加发布版本对比、回滚和发布说明。
- 优化执行记录页面，支持按节点查看输入、输出、耗时和错误。
- 增加 Webhook Trigger、定时 Trigger、邮件通知等常用自动化能力。
- 增加工作流导入、导出，方便迁移和分享。

### 2.2 AI 与 RAG 能力

建议逐步增强：

- 支持更多 Embedding provider，不只依赖 Ollama。
- 支持更多 LLM provider，让部署环境更灵活。
- 增加 rerank 阶段，提高 RAG 召回结果排序质量。
- 增加引用来源展示，让答案可以追溯到具体文档和切片。
- 优化 chunk 策略，支持按 Markdown 标题、代码块、表格等结构切分。
- 增加 RAG 测试集和评分机制，用于观察召回质量变化。
- 增加知识库重建索引能力，方便模型或切片参数变更后重新处理。

### 2.3 执行引擎

后续可以把执行引擎做得更可靠：

- 节点级超时、重试、失败策略。
- DAG 允许时的并行执行。
- 执行取消和中断恢复。
- 持久化执行队列，避免服务重启导致任务丢失。
- LLM 节点流式输出。
- 节点输出 schema 校验。
- 工作流输入输出 schema 管理。

### 2.4 工程化与稳定性

建议补齐：

- 为核心 executor、retriever、API route 增加自动化测试。
- 将构建、lint、format、typecheck 接入 CI。
- 统一生产部署脚本和回滚脚本。
- 增加数据库 migration 检查。
- 增加日志格式规范和错误码规范。
- 增加 API rate limit 和审计日志。
- 定期清理无效文档、失败任务、历史执行记录。

### 2.5 建议路线

可以按三个阶段推进：

| 阶段     | 目标         | 重点                                   |
| -------- | ------------ | -------------------------------------- |
| 第一阶段 | 个人稳定可用 | 部署、备份、基础监控、核心流程可跑通   |
| 第二阶段 | 提升完成度   | 模板、发布管理、执行记录、RAG 引用来源 |
| 第三阶段 | 产品化       | 权限、审计、队列、CI/CD、多模型适配    |

## 3. 本项目 RAG 流程

### 3.1 数据存储边界

RAG 相关数据分为两类：

- PostgreSQL：存知识库、文档、切片元信息、处理状态、模型配置、检索配置等结构化业务数据。
- Qdrant：存切片向量、切片 payload，以及用于向量检索和全文检索的内容字段。

也就是说，PostgreSQL 负责“业务状态和关系”，Qdrant 负责“检索”。

### 3.2 文档入库流程

用户上传知识库文档后，整体流程是：

1. 前端选择知识库并上传文档。
2. API 校验用户权限和知识库归属。
3. API 在 PostgreSQL 中创建 Document 记录。
4. 文档处理服务把 Document 状态改为 `PROCESSING`。
5. 根据文档类型选择文本切分器。
6. 按知识库配置的 `chunkSize` 和 `chunkOverlap` 生成 chunks。
7. 调用 Embedding 服务生成每个 chunk 的向量。
8. 确保 Qdrant collection 存在。
9. 把 chunk 向量和 payload 写入 Qdrant。
10. 更新 PostgreSQL 中 Document 状态为 `COMPLETED`。
11. 更新 KnowledgeBase 的文档数量和切片数量。

如果处理失败，Document 会被标记为 `ERROR`，并记录错误信息。

### 3.3 检索流程

当用户测试知识库搜索，或者工作流执行到知识库节点时，会进入检索流程：

1. 读取知识库配置。
2. 根据用户输入或节点配置得到 query。
3. 创建 Embedding 服务。
4. 创建 Qdrant Vector Store。
5. 创建全文检索 provider。
6. 根据知识库配置选择检索模式。
7. 返回 topK、score、content、metadata、documentId 等结果。
8. 在工作流节点中把结果整理为文本或 JSON 输出。

### 3.4 三种检索模式

#### Vector 检索

Vector 检索适合语义相似问题。

流程：

1. 对 query 生成 embedding。
2. 在 Qdrant 中按向量相似度搜索。
3. 使用 `knowledgeBaseId` 过滤当前知识库。
4. 使用 threshold 过滤低分结果。
5. 返回相似度最高的 topK 个 chunks。

特点：

- 能找到语义接近但字面不完全一致的内容。
- 依赖 embedding 模型质量。
- 对专业术语、短关键词的精确命中不一定最好。

#### Fulltext 检索

Fulltext 检索适合关键词精确匹配。

流程：

1. 按 `knowledgeBaseId` 从 Qdrant payload 中读取候选 chunks。
2. 对 content 做文本匹配。
3. 根据关键词命中情况计算分数。
4. 过滤低于 threshold 的结果。
5. 返回 topK 个 chunks。

特点：

- 对明确关键词、编号、字段名、专有名词更直接。
- 不依赖 embedding。
- 无法理解语义相近但字面不同的表达。

#### Hybrid 检索

Hybrid 检索适合默认生产使用。

流程：

1. 同时执行 Vector 检索和 Fulltext 检索。
2. 两边各自取比 topK 更多的候选结果。
3. 使用 Reciprocal Rank Fusion 合并排序。
4. 根据 `vectorWeight` 调整语义检索和关键词检索的权重。
5. 返回最终 topK 个 chunks。

特点：

- 同时兼顾语义相似和关键词命中。
- 默认体验通常比单一模式更稳。
- 调参重点是 topK、threshold 和 vectorWeight。

### 3.5 在工作流中的使用

知识库节点执行时，会把检索结果写入节点输出。

常见输出包括：

- `output`：整理后的文本结果，方便直接给 LLM 节点使用。
- `results`：结构化检索结果，包含 content、score、metadata 等。
- `count`：命中的结果数量。
- `query`：本次检索使用的查询文本。
- `mode`：本次使用的检索模式。

后续节点可以通过变量引用这些输出，例如把知识库节点的 `output` 拼进 LLM 节点 prompt。

## 4. 上下文管理

### 4.1 上下文的含义

本项目里的“上下文”主要分为两类：

- 执行上下文：一次工作流运行期间，节点之间传递的数据、变量、输入输出和执行状态。
- UI 上下文：前端页面中用于管理工作流编辑器、知识库、应用状态的 React Context。

它不是长期聊天记忆，也不是自动保存的用户历史偏好。

### 4.2 执行上下文

执行引擎在每次运行工作流时会创建一个 Execution Context。

它通常包含：

- executionId：本次执行的唯一标识。
- workflow：当前运行的工作流定义。
- inputs：本次运行传入的外部输入。
- variables：节点输出变量存储。
- completedNodes：已经执行完成的节点集合。
- startTime：本次执行开始时间。
- graph：由工作流节点和边构建出的执行图。
- variableResolver：变量解析器。

这个上下文只在本次工作流执行期间有效。

### 4.3 节点之间的数据上下文

节点之间的数据上下文，指的是“上游节点的输出可以作为下游节点的输入”。

例如：

1. 开始节点接收用户输入 `content`。
2. 知识库节点用 `content` 作为 query 做检索。
3. 知识库节点输出 `output` 和 `results`。
4. LLM 节点在 prompt 中引用知识库节点的 `output`。
5. 结束节点输出 LLM 的最终回答。

在这个过程中，每个节点执行完成后，都会把自己的 outputs 写入变量存储。下游节点执行时，可以通过变量表达式读取这些 outputs。

### 4.4 变量解析

项目中通过变量表达式把节点输出注入到下游节点配置中。

典型形式：

```text
${nodeId.output}
${nodeId.results}
${nodeId.count}
```

如果整个字段就是一个变量表达式，解析结果可以保留原始数据类型。例如结果数组仍然可以是数组。

如果变量出现在一段文本中，会被插值成字符串。例如：

```text
请基于以下资料回答问题：
${knowledgeNode.output}
```

这样 LLM 节点不需要直接知道知识库节点的内部实现，只需要消费上游节点提供的变量。

### 4.5 前端 UI 上下文

前端也有自己的 Context，用于管理页面状态。

常见职责包括：

- 当前应用信息。
- 当前工作流画布状态。
- 节点配置面板状态。
- 知识库列表和详情。
- 可供当前节点选择的上游变量。

前端 UI 上下文主要服务编辑体验；真正运行时的数据传递由执行引擎的 Execution Context 完成。

### 4.6 当前上下文管理的边界

当前机制的特点：

- 一次执行有一个独立上下文。
- 节点输出只在本次执行中作为变量使用。
- LLM 节点没有自动长期记忆。
- RAG 检索结果需要显式传给 LLM 节点。
- 如果需要跨执行保存状态，需要写入数据库或新增专门的记忆模块。

后续如果要增强上下文能力，可以考虑：

- 增加全局变量和工作流级变量。
- 增加类型化变量 schema。
- 增加运行历史引用能力。
- 增加可控的长期记忆模块。
- 增加上下文窗口裁剪和摘要策略。
